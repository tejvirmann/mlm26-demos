SLIDE 1 — "MCP vs API" (title already exists — add this body)
====================================================================

SLIDE CONTENT:
- An API is a contract you write custom code against, one integration per service
- MCP (Model Context Protocol) is a standard way to plug tools/data into ANY agent — write the integration once, every MCP-compatible agent can use it
- With an API, you write the calling code. With MCP, the agent discovers the available tools itself and decides when to call them
- Anthropic open-sourced MCP in Nov 2024. Now supported by Claude, Copilot, and others
- Use MCP when you want an agent to autonomously reach external systems (GitHub, Slack, a database). Use a direct API call when you're writing deterministic pipeline code yourself

SPEAKER NOTES:
Say: "Quick distinction before we demo this. An API is something YOU write code
against — you read the docs, you write the request, you parse the response.
MCP flips that: it's a standard protocol so an agent can discover a tool and
call it on its own, without you writing the plumbing."
Mention: this is why MCP matters for agentic coding specifically — the agent
is the one deciding when to reach for GitHub, a database, Slack, etc., not you.
Keep this short (30-45 sec) — it's the setup for the demo on the next slides.

SLIDE 2 — "What is an MCP server?"
====================================================================

SLIDE CONTENT:
- A lightweight server that exposes tools, resources, and prompts to an agent over a standard protocol
- Runs locally over stdio, or remotely over HTTP/SSE
- Examples: GitHub MCP, filesystem MCP, Slack MCP, Postgres/database MCPs
- The agent lists available tools when the session starts, then calls them like any built-in tool
- Anyone can write one — it's just a small program that speaks the MCP spec

SPEAKER NOTES:
Say: "An MCP server is just a small program. It says 'here are the tools I
offer' — like search_issues, or run_query — and the agent's client (Claude
Code, Copilot, Claude Desktop) connects to it and adds those tools to what
the model can call."
Analogy that lands well: "Think of it like installing a plugin — you're not
writing new agent code, you're handing the agent a new capability."
Flag the security angle briefly since it was covered earlier in the deck:
only add MCP servers you trust, since tool output goes straight into the
agent's context and it will act on it.

SLIDE 4 — "What is a Skill?"
====================================================================

SLIDE CONTENT:
- A Skill is a packaged, reusable set of instructions — a folder with a SKILL.md file, plus optional scripts/resources — the agent loads on demand
- Unlike MCP, a Skill needs no running server or network connection. It's just instructions and files bundled together
- Triggered automatically when the task matches, or invoked directly with /skill-name
- Good for repeatable workflows: a code review checklist, a repo-specific deploy process, a data-formatting spec
- Skills reduce token usage too — instead of re-explaining a process every time, the agent loads a short pointer and only pulls in the full instructions when needed

SPEAKER NOTES:
Say: "If MCP is a plugin that gives the agent a new tool, a Skill is more
like a playbook — a set of written instructions for doing one job well,
that the agent can load without you re-explaining it every session."
Contrast directly with MCP again since people conflate the two: "No server,
no network call — it's markdown and maybe a script, sitting in a folder."
Bridge to token usage: mention that Skills are literally one of the bullets
on the upcoming 'reduce token usage' slide, since the agent only expands the
full skill content when it's actually relevant instead of it sitting in
context the whole session.

SLIDE 5 — "Demo: Activate a Skill"
====================================================================

SLIDE CONTENT:
- List available skills: `/skills`, or look in `.claude/skills/`
- Invoke directly: `/<skill-name> [arguments]`
- Or just describe the task in plain language — Claude checks the skill list and loads the matching one automatically
- A skill can run inline in the current conversation, or hand off to a background subagent, depending on how it's defined
- Team/project skills live in the repo (`.claude/skills/`) so everyone on the team gets them automatically

SPEAKER NOTES:
Live demo:

2. Trigger one two ways, back to back, so the contrast is obvious:

   b. Implicitly: describe a task in plain English that matches a skill's

3. Call out that this second path is why writing a good one-line skill
   description matters — it's how the agent decides when to reach for it.

SLIDE 6 — "MCP & Skills: quick reference" (recap slide before moving to Cost/energy)
====================================================================

SLIDE CONTENT:
              MCP                          Skill
Purpose       New capability/tool          Reusable instructions/workflow
Needs         A running server             Just files (markdown + optional scripts)
Setup         claude mcp add               Drop a folder in .claude/skills/
Best for      Reaching external systems    Repeatable process, house style, checklists
Network       Often yes                    No (unless the skill itself calls something)

- Rule of thumb: reach for an MCP when the agent needs to DO something external. Reach for a Skill when the agent needs to KNOW how you want something done.

EXISTING SLIDE — "Techniques to reduce token usage" (content already present,
adding speaker notes only, since you're demoing these live)
====================================================================

EXISTING SLIDE CONTENT (for reference, no change needed):
- Pay attention to usage. (/cost)
- Police what model you are using and its level of difficulty. Make sure to switch.
- Minimize context used in prompts. (/compact, etc)
- Use sparingly.
- Use skills (graphify, caveman for ex.) to reduce input/output context.

SPEAKER NOTES:
This slide has three live demos packed into it — sequence them in this order:

1) /cost — checking usage
   Say: "First, just look at what you're spending." Run `/cost` in the
   terminal. Explain what's shown (context/session usage). Tie back to the
   safety section: this is also how you catch a runaway agent burning tokens
   on retries.

2) Switching models
   Say: "Not every task needs your most expensive model." Show how to switch
   (e.g. `/model` command or picking a lighter model for a simple task vs. a
   heavier one for a hard refactor). Make the point explicit: match model
   cost to task difficulty — don't run a trivial rename through your top-tier
   model by default.

3) /compact — minimizing context
   Say: "As a session runs long, old context piles up and every future
   message re-pays for it." Run `/compact` live, and briefly explain what it
   does: summarizes/trims the conversation so far so future turns cost less,

Close the slide by looping back to Skills: "This is also why Skills help

explanation every time, it's loading a short pointer only when needed."
